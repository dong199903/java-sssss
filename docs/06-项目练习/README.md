## 做什么

**地方社区交流系统**：小区帖子、评论、点赞、收藏、附近、热榜、通知。读远多于写，流量集中在列表和详情。

分五阶段。01～03 按顺序做，前一阶段验收表全部勾完再开下一阶段。04 是补在这个系统上的需求：阶段一出口后做甲（G1～G14），阶段二出口后做乙，阶段三出口后做丙。05 在通知能按当前用户查询之后做，只拆通知。

| 阶段 | 文档 | 做完你要能独立讲清 |
|------|------|-------------------|
| 01 单体 | [社区单体需求](01-社区单体/README.md) | 穿透 / 击穿 / 雪崩、先改库再删缓存、浏览量刷库、热榜衰减、点赞幂等、通知异步批量、越权、五容器部署 |
| 02 拆分 | [微服务拆分需求](02-微服务拆分/README.md) | 网关、注册发现、Feign、超时熔断、跨库后点赞计数如何最终一致 |
| 03 集市 | [秒杀与库存一致性需求](03-秒杀与库存一致性/README.md) | 同库本地事务扣库存、本地消息表、Redis Lua 预扣、延迟关单、对账 |
| 04 补强 | [岗位补强需求](04-岗位补强/README.md) | 请求编号、登录限流、游标列表、本地缓存、有界线程池、点赞 outbox、降级、停机和三份排查记录 |
| 05 分库分表 | [分库分表需求](05-分库分表/README.md) | 选错键会广播、通知按接收人拆到两个库、扩到 4 个分片时要重算路由 |

阶段一的技术栈按这条线锁定，后面只加组件，不换掉已掌握的中间件：

Java 21、Spring Boot 3.2、MyBatis-Plus、MySQL 8、Redis 7、Redisson、RabbitMQ、Docker Compose。前端以 [`community-hub`](community-hub/README.md) 现有的 React 为准。

简历里的「RabbitMQ 7」没有对应发行版。本练习使用 **RabbitMQ 4.x**（`rabbitmq:4-management`）。面试报实际镜像版本。

每一行都要在代码和验收里出现。只在文档里写过，不算掌握。

|-------------|------|------|------------|
| Java 21 | 编译版本；入参、出参用 `record` | 01 | `java -version` 为 21，接口 DTO 是 record |

| Redis 7 | 详情/列表缓存、`INCR`、ZSET | 01 | 热点详情第二次请求不打数据库 |

| 热榜 | ZSET 加权，30 分钟 ×0.8，低于 1 移出 | 01 | 点赞/评论/收藏后分数按权重增加；衰减后低分消失 |
| 点赞幂等 | `post_like` 唯一索引 | 01 | 同一用户并发点赞只落 1 行，计数只 +1 |
| RabbitMQ | 手动 ack、死信、批量消费 | 01 | 通知不在发帖接口里同步插入；失败进死信 |
| 通知去重 | 唯一索引 + 批量插入 | 01 | 同一事件重复投递不产生第二行通知 |
| 越权 | 登录态校验资源归属 | 01 | 改他人帖、看他人通知、非管理员看日志，全部拒绝 |
| Docker Compose | MySQL、Redis、RabbitMQ、后端、前端 | 01 | 一条命令起来，浏览器能走通发帖到通知 |
| 压测 | JMeter 打热点读 | 01 | 自己跑出回源次数、错误数、P99，写进验收记录 |
| React | 列表、详情、互动、热榜、通知、秒杀页 | 01 / 03 | 不靠 curl 也能完成主路径 |
| Nacos | 服务注册 | 02 | 停掉某个服务后网关发现实例消失 |
| Gateway | 统一入口、转发、秒杀路由限流 | 02 / 03 | 浏览器只访问网关端口 |
| OpenFeign | 跨服务查询 | 02 | 互动服务发赞前确认帖子存在 |
| 超时与熔断 | 调用方有超时；连续失败后熔断 | 02 | 下游挂起时调用在超时内返回，不把线程拖死 |
| 跨服务计数 | 点赞库与帖子计数库分开，靠消息对齐 | 02 | 没有跨库事务；重复消息不重复加计数 |
| 本地事务扣库存 | 订单与库存同一库同一事务 | 03 | 任一语句失败则订单和库存一起回滚 |
| 本地消息表 | 业务提交与发消息同一事务，定时补发 | 03 | 进程在「提交之后、发出之前」杀掉，消息仍会发出 |
| 秒杀 Lua | 库存、是否已买、扣减一次完成 | 03 | 100 库存、500 并发，成功单不超过 100 |
| 延迟关单 | TTL + 死信 | 03 | 超时未支付的单关闭，库存加回 |
| 对账 | Redis 预扣、数据库库存、成功订单三方核对 | 03 | 人为制造一条不一致后，任务能发现并留下记录 |

Seata 不作为本项目主路径。阶段三要求你能说明秒杀用预扣加对账、普通下单用本地消息表的原因。有余力再做一次 AT 对照，失败也不挡住验收。

## 怎么使用这份计划

1. 按 01 → 02 → 03 做。阶段一验收表有空项，不拆服务。04 穿插在对应阶段出口之后，不替代前三阶段。05 在通知能按当前用户查询之后做。
2. 每个需求编号（如 C3、K2）对应一块实现和至少一条自动化测试或一次你亲手执行的检查。
3. 压测数字以你机器上的记录为准。计划里出现的 99.8%、P99、1.4 万 QPS 是这条架构要去对的**参考标尺**，写进简历之前必须是你自己跑出来的数。
4. 阶段一结束时，你应能不看文档画出：一次详情读、一次点赞、一次通知，分别动了哪些表、哪些 key、哪条消息。
5. 对应阶段做完后，用下面的模拟面试自己讲。项目或原理有一列讲不出，就打开「去学」，看完再讲一遍。
