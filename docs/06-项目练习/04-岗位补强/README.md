# 04 岗位补强

[← 上一阶段：秒杀与库存](../03-秒杀与库存一致性/README.md) | [项目练习](../README.md) | [下一阶段：分库分表 →](../05-分库分表/README.md)

在已经做完的社区系统上补能力。业务不变，不新开项目。按下面编号实现，做完一条就勾一条。

某一条里的概念还不熟，先看文末「卡住时看哪里」，看完再回来写代码。

## 1. 目标

阶段一到阶段三做完，系统已经能发帖、缓存、拆服务、秒杀。本阶段补上这些能运行的行为：

- 一次请求能用同一个编号把日志串起来。登录会过期，注销会失效，连续输错密码会被挡住。
- 列表不靠越翻越深的页码。热点详情在进 Redis 之前先打到本机缓存。刷浏览和发通知的线程池有上限。
- 点赞计数在消息乱序、进程在发出消息前被杀掉时仍然对。用户服务或热榜挂了，看帖还在。
- 你亲手留下连接池打满、CPU 栈、内存溢出这三份记录。

前端继续用 community-hub 里的 React。本阶段只改登录态、请求头和点赞失败时的界面，不换框架。

## 3. 技术约束

沿用阶段一的 JDK 21、Spring Boot 3.2、MyBatis-Plus、MySQL 8、Redis 7、Redisson、RabbitMQ、Docker Compose。

本阶段允许新增的库只有 Caffeine（本地缓存）。鉴权继续用现有 JWT 过滤器，不改成 Spring Security。

接口仍然是 `code / message / data`。校验失败 400，未登录或令牌失效 401，越权 403，资源不存在 404。

## 4. 甲：阶段一做完后补

### G1 请求编号

1. 请求头有 `X-Request-Id` 就沿用，没有就生成一个。
2. 放进日志上下文，响应头原样返回。
3. 业务错误日志和慢 SQL 日志都带这个值。
4. 日志和响应里不出现明文密码、密码哈希。

通过：改一次帖，用响应头里的编号，在应用日志和 SQL 日志里各搜到一行。

### G2 令牌过期、注销、登录限流

过滤器顺序固定为：请求编号 → 登录限流 → 解析令牌 → 黑名单 → 控制器。

1. 访问令牌有效期不超过 2 小时。过期后再访问，返回 401。
2. 注销把该令牌的 `jti` 写入 Redis，保留到令牌原过期时间。之后再用这张令牌访问，返回 401。
3. 同一用户名连续密码错误 5 次后，1 分钟内不再校验密码，返回明确业务错误。计数在 Redis。

通过：三条各有一个自动化测试。

### G3 改帖只改允许的字段

`PUT /api/posts/{id}` 的请求体只采用标题、正文、经纬度。带上 `authorId`、`likeCount`、`viewCount` 时，这些列在数据库里不变。

列表、附近、详情的条件使用预编译参数，SQL 日志里是 `?`。小区名里含有引号和注释符时，按普通字符串查询，条件不被改写。

通过：上述两条都有测试。

### G4 小区列表改为游标

主列表改为：

```text
GET /api/posts?communityId=&cursor=&limit=20
```

`cursor` 是上一页最后一条的 `created_at` 和 `id`。第一页不带 cursor。查询条件：

```sql
WHERE community_id = ?
  AND (created_at < ? OR (created_at = ? AND id < ?))
ORDER BY created_at DESC, id DESC
LIMIT ?
```

`EXPLAIN` 使用 `idx_community_created`（排序需要时把索引扩成 `community_id, created_at, id`），`type` 不是 `ALL`，Extra 里没有 `Using filesort`。

深分页只做对照：对 `LIMIT 100000, 20` 跑一次 `EXPLAIN`，把扫描行数写进文末记录。线上列表不再提供大 offset。

一页帖子上的作者昵称，用一次 `IN` 或一条 JOIN 查完。这一页对 `user` 表只有 1 次查询。

### G5 详情的本地缓存

读详情的顺序：本机缓存 → Redis → 阶段一的加锁回源。

1. 使用 Caffeine。TTL 10 秒。最大条目 1000。
2. 本进程内改帖、删帖成功后，删掉本机缓存和 Redis 详情 key。
3. 其他进程不收到通知，最多 10 秒后自己过期。

通过：同一进程连续两次命中本机缓存时，没有对应的 Redis GET。改标题后，本进程下一次详情已是新标题。阶段一的空值标记、互斥回源仍然有效。

### G6 两个有界线程池

刷浏览量、批量插入通知，各用一个 `ThreadPoolExecutor`。禁止使用 `Executors.newFixedThreadPool` 和 `Executors.newCachedThreadPool`。

每个池写明：核心数、最大数、队列容量、线程名、拒绝策略。数字记在文末记录里。

刷浏览的队列满了时，已从 Redis 读出的增量不能丢：由调用线程自己刷，或者把帖子 id 留在 `post:view:dirty`。

处理 HTTP 的线程继续用平台线程。持有 Redisson 锁的代码、以及包在 `synchronized` 里的批处理，不提交到虚拟线程。用或不用虚拟线程，在文末记录里写一句决定。

### G7 死锁演练

写一个测试或脚本：两个事务以相反顺序更新同一篇帖子和它的一条评论（或另一张相关行），能够产生死锁。把 `SHOW ENGINE INNODB STATUS` 里的死锁段落贴进文末记录。

然后规定加锁顺序：先帖子主键，再子表主键。修完后，同一测试不再稳定出现死锁。

点赞仍保持阶段一的写法：唯一键插入和计数加减在同一个事务里。

### G8 连接池打满

只在测试配置里把 Hikari 最大连接改为 2，并提供一个占住连接不归还的接口。并发调用普通业务接口，直到出现获取连接超时。日志能看出是在等连接。

测完把最大连接改回日常值。占住连接的接口不出现在默认配置里。把池大小和超时日志摘要写入文末记录（P-POOL）。

### G9 停机

配置 `server.shutdown=graceful`，并设置超时时间。进程收到停止信号时：

1. 正在处理的 HTTP 请求允许做完。
2. 把当前 `post:view:dirty` 再刷一次库。没刷完的增量留在 Redis，下次启动继续刷。
3. 先停止 RabbitMQ 监听，把已经取到的消息处理完再退出。没处理完的消息保持未 ack，以便重新投递。

通过：刷库过程中停止进程再启动，停止前已经 `INCR` 的浏览最终出现在 `view_count`。不要求 `kill -9` 时也刷成功。

### G10 点赞幂等打到真实 MySQL

至少一条测试连接真实 MySQL（Testcontainers 或本机练习库）。同一用户对同一帖并发点赞，表中 1 行，`like_count` 只加 1。只 mock Mapper 的测试可以保留，不能代替这一条。

### G11 发帖幂等

发帖请求带客户端生成的 `requestId`。同一作者、同一 `requestId` 再次提交，返回原来的帖，不插入第二行。表上有对应唯一约束。

### G12 前端三处行为

在现有 React 页面上：

1. 请求带上访问令牌和 `X-Request-Id`。
2. 收到 401 时清除本地登录态，进入登录页。
3. 点赞可以先改页面上的数字。请求失败则改回去。请求成功后，数字以响应体为准。

### G13 异常分层

已点赞、卖完、未登录、参数不合法，使用业务异常，响应里的 `code` 稳定。SQL 异常、拿不到连接、空指针不把数据库原文或堆栈返回给前端，记在服务端日志里，并带上 G1 的请求编号。

通过：唯一键冲突返回业务错误；故意制造一条 SQL 错误时，响应体里没有 SQL 原文。

### G14 回源锁的租约

阶段一的 `lock:post:{id}` 租约保持 10 秒。在构造锁的代码旁写明：

1. 设了租约之后，Redisson 不会按看门狗续期。
2. 回源查库和写缓存必须在 10 秒内结束。
3. 锁过期后，另一个请求可以再查库。阶段一的双重检查仍然要在，避免两个请求同时写缓存。

把「租约 10 秒、看门狗关闭」写进文末记录。

## 5. 乙：阶段二做完后补

阶段二的超时、熔断、`consumed_event` 保持不变。

### S1 列表昵称一次查完

内容服务组装一页帖子时，按用户 id 批量调用用户服务一次。禁止按帖子循环调用。

连接超时 200ms，读超时 500ms。用户服务不可用时，列表仍返回 200，昵称用空字符串，日志带请求编号。帖子标题照常返回。

### S2 热榜降级

互动服务停止或熔断打开时：

1. 详情和列表仍可访问（阶段二 D3）。
2. `GET /api/ranks/hot` 在超时时间内返回 200。响应体包含 `degraded: true`，列表为空，或返回上一份成功结果。选哪一种，写在接口注释里。
3. 这个失败不能让网关把其他接口变成 500。

### S3 调用用户服务的并发上限

内容服务调用 S1 的批量接口时，使用单独的有界并发（舱壁或有界线程池）。用户服务一直不返回时，发帖接口在它自己的超时内结束，内容库的连接池不被占满。

通过：演练或测试里能看到发帖成功（或按发帖自己的错误返回），而不是等满连接池超时。

### S4 点赞计数按增量各算一次

内容服务消费计数消息时，按 `delta` 直接加减，同一 `eventId` 只应用一次。不要用「`like_count > 0` 才允许减 1」处理跨服务的取消。

通过：先投递 `delta = -1`，再投递 `delta = +1`，最终 `like_count` 为 0，`post_like` 为 0 行。两条消息再各投递一次，计数仍是 0。

### S5 点赞计数与 outbox 同一事务

在互动库中，插入 `post_like` 和插入 outbox 放在同一个本地事务。outbox 字段与阶段三相同：`event_id` 唯一，`status` 0 待发送、1 已发送。

事务提交后发送。发送成功再把该行标为已发送。每 10 秒扫描仍为待发送、且创建超过 5 秒的行，再次发送。

通过：事务提交后不调用发送方法，只留下 `status = 0` 的行。启动补发后，`like_count` 只加 1。

通知仍按阶段一在事务提交后发送。计数走本节，通知不走本节。

### S6 请求编号跨服务

网关把 `X-Request-Id` 传到下游。Feign 调用和点赞计数消息都带上它。一次点赞的网关日志、互动服务日志、内容服务消费日志是同一个编号。

## 6. 丙：阶段三做完后补

### K1 订单状态

允许的迁移只有：

- 链路乙的排队中 → 待支付，或排队中 → 已关闭
- 待支付 → 已支付
- 待支付 → 已关闭

已关闭再支付，返回业务错误，库存不变。已支付再支付，不产生第二笔成功，库存不变。已支付收到关单消息时，保持已支付，库存不回加（阶段三 K6）。

### K2 对账记录可查询

`GET /api/admin/reconcile-logs?activityId=` 仅管理员可访问。按活动返回 `reconcile_log`，只读。任务仍然只插入记录，不改库存和订单。

### K3 三份排查记录

每份都写进文末的表：做了什么、看了哪条日志或哪条命令、结论是什么。

| 编号 | 做法 | 记录里要有 |
|------|------|------------|
| P-POOL | 完成 G8 | 池大小、超时日志、改回配置后一次成功请求 |
| P-CPU | 压测秒杀，或临时写一段死循环后抓栈。抓完删除死循环代码 | `jstack` 或 `jcmd Thread.print` 的输出摘要，并标明是业务线程、等锁，还是 GC |
| P-OOM | 在测试里循环创建大对象，或把本地缓存上限临时放到极大，打开堆转储。测完恢复 G5 的 1000 条上限，删掉造数据的代码 | 转储文件里占用最高的对象类型 |

另外再完成下面两份中的一份：

| 编号 | 做法 |
|------|------|
| P-SLOW | 去掉附近查询的索引，确认慢日志里出现这条 SQL。把 `EXPLAIN` 贴上。索引加回后，`type` 恢复 |
| P-COUNT | 按 S4 先投递取消。修复前记下错误计数，修复后记下 0 |

### Y1 流量变大时用哪些已有能力

在文末记录里写一段，不新增组件。假设详情和秒杀的流量变成平时的 3 倍，按顺序写出你会依靠的现有能力，并写明你认为会先打满的是数据库连接还是 Redis 上的单个详情 key。

必须用到已经实现的：G5 本地缓存、阶段三网关限流、秒杀队列、S2 热榜降级、G4 游标列表。
