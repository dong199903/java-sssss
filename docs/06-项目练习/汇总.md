## 01 单体

做一个进程、一个库。读帖走缓存，写帖改库后再删缓存，通知走消息。

| 要掌握 | 用在 | 原理 |
|--------|------|------|
| Java 21，接口的入参出参用 `record` | 全部接口 | — |
| Spring Boot 接口、参数校验、`@Transactional`、`@Scheduled` | 发帖、点赞、浏览刷库、热榜衰减 | [事务](../04-spring/05-transaction/README.md) |
| 事务提交成功后再删缓存（`afterCommit`） | 改帖、改计数。回滚则不删 | [缓存](../03-redis/05-cache-problems/README.md) |
| MyBatis-Plus 分页和条件构造，主键用雪花 | 列表、写入 | [MyBatis](../05-other/05-mybatis/README.md) |
| 建表、唯一索引、二级索引，会看 `EXPLAIN` | 9 张表；列表走 `idx_community_created`；附近走 geohash 范围，不用 `LIKE '%xx'` | [索引](../02-mysql/04-index-use/README.md) |
| 同一事务里：插入关系行成功才给计数加 1 | 点赞、收藏、评论。并发点赞只有 1 行 | [隔离级别](../02-mysql/05-isolation/README.md) |
| Redis 字符串、集合、ZSET；`INCR`；TTL 加随机秒 | 详情、列表、浏览量、热榜 | [数据结构](../03-redis/02-data-types/README.md) |
| 缓存穿透（空值）、击穿（加锁后再查一次）、雪崩（TTL 错开） | 帖子详情 | [缓存问题](../03-redis/05-cache-problems/README.md) |
| Redisson 锁，没抢到锁的请求不写缓存 | 详情回源 | [分布式锁](../03-redis/06-dist-lock/README.md) |
| 删一批 key 用 `SCAN`，不用 `KEYS` | 某个小区的列表缓存 | [缓存问题](../03-redis/05-cache-problems/README.md) |
| 浏览量先 `INCR`，定时用 Lua 取出并刷进数据库 | `view_count` 可以慢一个周期；点赞数不行 | [数据结构](../03-redis/02-data-types/README.md) |
| 热榜 `ZINCRBY`，定时乘 0.8，Redis 清空后能从数据库重建 | 点赞 +2、评论 +3、收藏 +4 | [数据结构](../03-redis/02-data-types/README.md) |
| RabbitMQ：topic、手动 ack、失败重试、死信、批量消费 | 通知不在发帖接口里插入 | [消息队列](../05-other/02-mq/README.md) |
| 消费端用唯一索引挡住重复消息 | `notification` 的去重键 | [消息队列](../05-other/02-mq/README.md) |
| 密码 BCrypt；未登录 401；改别人的资源 403 | 注册登录、越权用例 Z1～Z5 | [过滤器](../04-spring/11-filter-interceptor/README.md) |
| Docker Compose 拉起 MySQL、Redis、RabbitMQ、后端、前端 | 一条命令启动 | — |
| 用压测工具打热点详情，记下回源次数、错误数、P99 | 阶段一验收表 | [场景](../05-other/06-scene/README.md) |
| React：登录、列表、附近、详情、发帖、热榜、通知 | 不靠 curl 走通主路径 | 代码在 [community-hub](community-hub/README.md) |

阶段一结束时能画出三张图：读一篇详情、点一次赞、发一条通知。每张图标出表、Redis key、消息。

## 02 拆分

四个业务服务加一个网关，每个服务自己的库。点赞和帖子计数不再放在一个事务里。

| 要掌握 | 用在 | 原理 |
|--------|------|------|
| 按数据归属拆表，服务之间不互相连库，不做跨库 JOIN | 用户、内容、互动、通知四个库 | [Spring Cloud](../04-spring/08-cloud/README.md) |
| Nacos 注册；进程停掉后实例消失 | 四个服务 | [Spring Cloud](../04-spring/08-cloud/README.md) |
| Gateway 转发，浏览器只访问网关 | 路径与阶段一相同 | [Spring Cloud](../04-spring/08-cloud/README.md) |
| OpenFeign，连接超时 200ms，读超时 500ms | 点赞前确认帖子还在 | [Spring Cloud](../04-spring/08-cloud/README.md) |
| 连续失败后熔断，熔断期间直接返回繁忙 | 停掉内容服务再点赞 | [Spring Cloud](../04-spring/08-cloud/README.md) |
| 本库事务提交后发消息；消费端用 `consumed_event` 保证同一条只加一次计数 | 点赞、取消、收藏 | [消息队列](../05-other/02-mq/README.md) |
| 详情里的点赞数允许暂时是旧的，消息消费并删缓存后变新 | 阶段二的接口测试 | [缓存问题](../03-redis/05-cache-problems/README.md) |
| 热榜只放在互动服务；详情缓存只放在内容服务 | 停掉互动服务，列表和详情仍能打开 | — |

阶段二结束时能讲清：一次点赞写了哪个库、发了哪两条消息、谁消费、哪张表挡住重复加一。

## 03 秒杀

同一个集市，三条链路都留着，后面的不替换前面的。

| 要掌握 | 用在 | 原理 |
|--------|------|------|
| `UPDATE ... WHERE stock > 0`，看影响行数，失败就回滚 | 链路甲：订单和库存同一事务 | [事务](../04-spring/05-transaction/README.md)、[锁](../02-mysql/07-locks/README.md) |
| 同一个 `requestId`、同一个用户，都不二次扣库存 | 链路甲 S2、S3 | [索引](../02-mysql/04-index-use/README.md) |
| 本地消息表：业务行和 outbox 同一事务，定时补发 | 链路乙。进程在发出前停掉，库存仍只扣一次 | [消息队列](../05-other/02-mq/README.md) |
| 消费端先插入 `consumed_event`，插入成功才扣库存 | 同一 `eventId` 投递两次只扣 1 | [消息队列](../05-other/02-mq/README.md) |
| Redis Lua：活动时间、是否买过、库存、扣减在脚本里一次做完 | 链路丙。100 库存、500 并发，成功单不超过 100 | [场景](../05-other/06-scene/README.md) |
| 数据库那条 `stock > 0` 仍然要执行。Lua 和数据库各挡一层 | 只做其中一层不算通过 | [锁](../02-mysql/07-locks/README.md) |
| 队列 TTL 15 分钟，死信后关单，库存加回 Redis 和数据库 | 测试里把 TTL 改成 5 秒 | [消息队列](../05-other/02-mq/README.md) |
| 对账只插入 `reconcile_log`，不自动改数 | 把 Redis 库存改大，任务能发现 | — |
| 网关对秒杀路径限流，多余请求到不了 Lua | 令牌桶或滑动窗口，阈值写在配置里 | [场景](../05-other/06-scene/README.md) |
| React 活动页：剩余名额、抢购、用订单号轮询 | 重复点击使用同一个 `requestId` | — |

阶段三结束时能讲清：点击之后 Redis、消息、数据库各写了什么；不支付时库存怎么回来。

## 05 分库分表

通知能按当前用户查到之后再做。帖子、订单、点赞不拆。

| 要掌握 | 用在 | 原理 |
|--------|------|------|
| 按作者拆帖子，小区列表会打两张表；见过日志后把帖子迁回一张表 | H1 | [MySQL 08](../02-mysql/08-optimize/README.md) |
| 通知按 `receiver_id % 2` 进入两个库，「我的通知」只打一个库 | H2、H3 | [MySQL 08](../02-mysql/08-optimize/README.md) |
| 唯一索引不包含分片键时，另一个库还能插入相同业务号 | H4 | [索引](../02-mysql/04-index-use/README.md) |
| 一个用户的通知在分片内用游标翻页；跨所有人的合并只留在测试里 | H5 | [MySQL 08](../02-mysql/08-optimize/README.md) |
| 扩到 4 个分片时按新取模重放数据，行数一致 | H6 | [MySQL 08](../02-mysql/08-optimize/README.md) |

## 整个项目做完，要能讲的五条

1. 读详情：本机缓存、Redis、锁、数据库，谁先谁后。
2. 点赞：哪张表保证只有一行，计数消息丢了怎么补，乱序为什么还是 0。
3. 通知：为什么可以重复投递，为什么可以在发出前丢掉。计数为什么不行。
4. 秒杀：Lua 挡一层，`stock > 0` 再挡一层；不支付时库存从哪加回去。
5. 一个依赖挂了：用户服务、热榜、内容服务，各自还剩什么功能。

## 这个项目不用再加的

做需求时遇到这些词，用现有实现回答，不要装进工程：

| 词 | 用哪一段回答 |
|----|----------------|
| 主从 | 详情走缓存。刚发的帖若读从库会看不到，第一次读走主库。见 [MySQL 08](../02-mysql/08-optimize/README.md) |
| 布隆过滤器 | 不存在的帖用阶段一的空值标记 |
| Elasticsearch | 查询是小区和 geohash 前缀 |
| 再加一个 Kafka | 延迟和死信用的是 RabbitMQ；计数可靠用的是 outbox |
| Seata | 同库用本地事务，跨库用 outbox，秒杀用预扣和对账 |
| Kubernetes | 用 Docker Compose 起依赖和服务 |
| 换成 Spring Security | 用阶段一的过滤器和 04 的 G2 |
