# 05 分库分表

[← 上一阶段：岗位补强](../04-岗位补强/README.md) | [项目练习](../README.md)

帖子、订单、点赞继续留在原来的单表上。这一阶段只拆通知，并先做一次选错分片键的对照。概念不熟时先看 [MySQL 08](../../02-mysql/08-optimize/README.md) 里分库分表那一段，再回来写。

自己计算落到哪一张表、哪一个库，SQL 日志里要能看见具体表名。用中间件把路由藏起来，不算通过。

## 1. 目标

做完要同时满足三件事：

- 按作者拆帖子时，小区列表一次请求打到两张表。你见过这条日志，然后把帖子迁回一张表。
- 通知按接收人拆开之后，「我的通知」只打一张表、一个库。
- 从 2 个分片改成 4 个分片时，数据按新规则重新放入，行数对得上。

## 2. 范围

阶段一的通知能写入、能按当前用户查询之后就可以做。服务已经拆开时，路由放在 notify-service 里。

帖子主路径在本阶段结束时必须回到一张 `post` 表。订单、库存、点赞、评论不拆。

同一台 MySQL 上建两个库就算分库，不必再起一台数据库。

## 3. 分片规则

通知的分片键是 `receiver_id`。

| 阶段步骤 | 库 | 表 | 路由 |
|----------|----|----|------|
| 分表 | 通知所在的那个库 | `notification_0`、`notification_1` | `receiver_id % 2` |
| 分库 | `notify_0`、`notify_1` | 每个库一张 `notification` | `receiver_id % 2` 选择库 |
| 扩容演练 | 四个库 `notify_0` 到 `notify_3`，或四张表 | 每个分片一张 `notification` | `receiver_id % 4` |

每张分表（每个库里的那张表）都建阶段一的去重唯一索引，列里包含 `receiver_id`。主键继续用雪花，不用分片内的自增。

`% 2` 等于 0 的人永远进 0 号分片，等于 1 的人永远进 1 号分片。扩到 4 个分片时，这个对应关系会变，不能假定原来在 0 号的人还在 0 号。

## 4. 需求

### H1 选错帖子的分片键

临时把 `post` 按 `author_id % 2` 拆成 `post_0`、`post_1`，数据拷进去。

小区列表按 `community_id` 查询。一次列表请求的 SQL 日志里要出现对两张表的查询，应用再把结果合并。

把这次日志摘要写进文末记录。然后把数据迁回一张 `post`，删掉 `post_0`、`post_1`。列表恢复为一条 SQL，`EXPLAIN` 仍走原来的小区索引。

通过：记录里有广播的证据，仓库里的帖子仍是一张表。

### H2 通知分表

插入通知时先算 `receiver_id % 2`，只插入对应的那一张表。

`GET /api/notifications` 只查当前用户所在的那一张表。SQL 日志里这一次请求只有一条通知查询。

不带 `receiver_id` 的查询可以留在测试里，用来看到两张表都被访问。这个查询不提供给前端。

通过：两个 `receiver_id` 奇偶不同的用户，各自的通知请求打到不同的表名。

### H3 通知分库

把 H2 的两张表挪到两个库 `notify_0`、`notify_1`，每个库一张 `notification`。应用按 `receiver_id % 2` 选择数据源。

查「我的通知」只连接其中一个库。两个库之间没有外键，也没有 JOIN。

阶段一的去重仍然有效：同一 `receiver_id + event_type + biz_id` 在该用户所在的库里只有一行。

### H4 唯一索引挡不住另一个分片

写一条测试：去掉分片键、只用 `biz_id` 做唯一索引时，两个库可以各有一行相同的 `biz_id`。

然后恢复「唯一索引包含 `receiver_id`」。再插入同一个接收人的重复通知，只能成功一行。

### H5 分片内的翻页

某个用户的通知列表使用 `created_at` 和 `id` 作为游标，SQL 只打他所在的那一个库。

另写一个仅测试或管理员可用的查询：从每个分片各取 20 行，在应用里按时间合并。日志里能看到每个分片一条 SQL。这个接口不作为用户看通知的主路径。

### H6 从 2 个分片扩到 4 个

新建 `notify_0` 到 `notify_3`（若 H3 已有 0 和 1，则补 2 和 3，并把数据按新规则重放）。路由改为 `receiver_id % 4`。

迁移任务读出旧分片的每一行，按新的取模插入新分片。迁移期间通知接口停止写入。迁完后：

- 全部新分片的行数之和等于迁移前的行数
- 抽 5 个用户，按新路由能查到迁移前属于他的通知

在文末记录里用几句话写明：若迁移时不能停写，新的写入要同时写旧规则和新规则，读仍走旧规则，对账通过后再切读、再停旧写。本阶段的代码只做停写迁移，双写不实现。

## 5. 出口

- [ ] H6 行数一致，5 个用户按新路由能查到自己的通知
